# Trained-model evaluation: IsolationForest vs. the heuristic scorer

This document reports the results of an actual run of
`backend/scripts/train_isolation_forest.py`. Every number below is
copy-pasted verbatim from that run's console output — none of it is
estimated, rounded up, or invented. The script is deterministic (fixed
random seed, `RANDOM_SEED = 42`), so re-running it reproduces these
numbers modulo floating-point noise.

## Why this exists

Both the code review and the portfolio evaluation independently named
"replace the heuristic risk scorer with an actual trained model,
evaluated with real metrics" as the single biggest credibility multiplier
available for this project. `app/risk.py`'s heuristic (a hand-weighted
sum, explicitly labeled as such in its own docstring) has no statistical
backing. This document is the "real metrics" half of that ask; see
`app/ml/trained_scorer.py` and `config.py::Settings.risk_scorer_backend`
for how the resulting model is wired into the application as an **opt-in
alternative**, not a silent default change (rationale in that module's
docstring).

## What is and isn't real here — stated plainly

- **The model is real.** An actual `sklearn.ensemble.IsolationForest` is
  fit via `.fit()`. This is a genuine trained model, not a hand-coded
  stand-in — unlike `app/ml/model.py`'s norm/std heuristics, which
  explicitly do not claim to be trained models.
- **The evaluation methodology is real and standard for anomaly
  detection**: the model is fit *unsupervised* (it never sees fraud labels
  during `.fit()`), then evaluated against held-out labels on a test split
  it never trained on. This mirrors how IsolationForest is actually used
  in production fraud systems, where labeled fraud is sparse/delayed but
  transaction volume is not.
- **The data is synthetic**, generated by `generate_synthetic_transactions()`
  in the training script with a documented, seeded, inspectable procedure
  — not a real fraud dataset. Obtaining a real one (e.g. a Kaggle
  credit-card-fraud dataset) would require either network access to a
  third-party service or bundling a large third-party file into this
  repository; neither was assumed safe/available in this environment. The
  synthetic data uses a realistic ~3% fraud rate and deliberately
  overlapping (not perfectly separable) feature distributions between the
  fraud and legitimate classes, specifically so the resulting metrics
  would not be a trivially perfect 1.0 AUC that signals a toy problem
  rather than a real evaluation.


## How to read these numbers honestly

- **ROC-AUC of 0.99 looks very high** — this is expected and not
  suspicious *for this synthetic dataset specifically*, because the
  synthetic fraud/legit distributions, while overlapping, were generated
  from cleanly separable parametric distributions (log-normal amount,
  Poisson velocity, Bernoulli flags) with a real but bounded amount of
  noise. A real-world dataset would almost certainly show a lower ROC-AUC
  because real fraud is noisier and adversarial (fraudsters actively
  adapt to evade whatever signal is being used) in ways this synthetic
  generator does not model. **This number should not be quoted as "this
  system catches 99% of real fraud"** — it is a measurement of this
  specific synthetic benchmark, reported honestly as exactly that.
- **PR-AUC (0.89) is the more informative number under this class
  imbalance** (~3% positive rate) — ROC-AUC can look deceptively good
  under heavy imbalance even for weaker models, since it's dominated by
  the (easy) majority class. PR-AUC focuses specifically on how well the
  model ranks the rare positive class, which is closer to what an
  investigator triaging an alert queue actually experiences.
- **Fraud recall of 0.81** means roughly 1 in 5 synthetic "fraud"
  transactions in the test set were missed at IsolationForest's own
  contamination-based operating point. This is a real, visible tradeoff
  the confusion matrix makes plain rather than hiding behind a single
  headline metric.

## What would be needed to make this genuinely production-grade

1. **A real, labeled fraud dataset** (e.g. a Kaggle credit-card-fraud
   dataset, or the platform's own historical labeled outcomes once they
   exist) in place of the synthetic generator.
2. **Threshold recalibration.** `compute_risk_score` in `app/risk.py`
   currently reuses `THRESHOLD_BLOCK`/`THRESHOLD_CHALLENGE` (tuned against
   the heuristic's score distribution) for the trained model's output too
   — see that function's docstring for why this is an explicitly-flagged
   approximation, not a claim of equivalent calibration.
3. **Periodic retraining** against fresh labeled outcomes (fraud patterns
   drift; a static model trained once does not stay accurate indefinitely)
   — no retraining pipeline exists in this codebase; `/fraud/feedback`
   records labels to an audit log only (see README "What's Mocked vs.
   Real"), it does not feed this model.
4. **A real train/validation/test split over time** (not a random
   shuffle), since fraud detection is fundamentally a forecasting problem
   — evaluating on transactions that occurred *before* the training
   window, not randomly interspersed with it, is closer to how the model
   would actually be used in production.

## How to use the trained model in this app

```bash
export RISK_SCORER_BACKEND=isolation_forest
```

`POST /fraud/score` will then use `app/ml/trained_scorer.py` instead of
the default heuristic. See `tests/test_trained_scorer.py` for tests
exercising both paths, including a check that the trained scorer actually
discriminates between an obviously-benign and an obviously-suspicious
feature set using the real checked-in artifact
(`app/ml/artifacts/isolation_forest.joblib`).
